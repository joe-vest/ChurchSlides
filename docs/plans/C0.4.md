| 4 | **Combinations compared:** readers `Mp3FileReader` and `MediaFoundationReader`; outputs `WaveOutEvent` (100 ms) and `WasapiOut` shared mode (50 ms and 100 ms). ## C0.4a: Audio measurements (first commit)

- `ChurchSlides.Spike.csproj`, `Directory.Packages.props`: `NAudio` (decision 1).
- `AudioFiles.cs`: finds MP3s, opens each with both readers, records CBR/VBR (Xing header), length by each reader, open time (`Mp3FileReader` scans the whole file), and builds the reference copies (decision 3).
- `SpikePlayer.cs`: one reader plus one output, play from Trim Start to Trim End (a sample provider that ends exactly at Trim End), stop, seek-and-play, position from both sources. Audio is streamed, never decoded whole (only the 11 kHz reference, released after the test).
- `LoopbackProbe.cs`: loopback capture of the default device, timed by captured sample count, and the correlation that maps capture time to file time.
- `DeviceWatch.cs`: decision 6.
- **Audio tab:** file, reader and output pickers; Play, Stop, Restart; Trim Start and Trim End boxes; position at 0.1 s (AUD-011); click on a position bar to seek and play (AUD-010); the device log.
- **Automatic run (S4):**
  - *Seek:* for every file and reader, seek to 12 positions (0.5 s, 3 s, 30 s, 2 min, near the end, 7 random), read 0.5 s, find the true position by correlation. Error per seek, mean and max, and seek time.
  - *Decoder offset:* the difference between the two readers' decodes of the same file (encoder delay). It matters for AUD-005: Cues are stored as file time, so changing decoder later would move every Cue by this much.
  - *Playback:* for each reader and output (8 runs of 20 s on the first VBR file), play from Trim Start to Trim End with loopback on. Records: first heard position against Trim Start, last heard position against Trim End, and reported position minus heard position for both sources (mean = the latency offset to subtract, p95 and max of what's left).
  - *Seek-and-play delay:* command to first heard sample from the new position, 5 times per combination (cue editor and Restart feel).
  - Working set and CPU while playing, per reader (PLT-005).

## C0.4b: Cues, ear checks and timer (second commit)

- `CueTest.cs`: on the Output monitor (C0.2b `SlideOutput` and `Presenter`), plays a song with a Cue every 2 s, each to a specific slide. The poller thread (decision 5) reads the best combination's position minus its measured offset and posts the slide change to the UI thread. Slides pre-render on the UI thread or the render thread. Lateness per Cue is from the moment the Cue position is heard (loopback) to the first frame showing its slide. Four runs of 40 s: pre-render on each thread, with and without `timeBeginPeriod(1)`.
- **Ear checks on the Audio tab:** *Sync*: the generated click track, the Output flashing white on each click (a Cue per click). *Tap*: play a song, press Space at the start of each line (AUD-008), then play it back and watch the Output change at the taps.
- `TimerOutput.cs`: background and static text as frozen bitmaps (as in C0.2b), one live slot `DrawingVisual` with each character centred in a fixed-width cell sized for the widest value, warning color at the threshold (TMR-006), minus sign when negative (TMR-005).
- **Timer tab (S5):** font and size picker, duration, warning threshold, run length (default 12 min). The automatic run counts down 11:00 with the warning at 1:00, then carries on negative, and crossfades for the second half (decision 7). Records: per tick, the time from the whole second to the frame showing it (mean, p95, max); seconds skipped or shown twice; drift of the plain `DispatcherTimer` at the end; slot redraw time; CPU % and working set with and without fades; dropped frames per fade against the S2 figure; digit advance-width spread of each tried font (how far proportional digits would move without cells).

## Pass criteria (proposed; final judgement at G0)

| # | Pass |
|---|---|
| S4-a | Seek error within 20 ms at every position on the church's VBR files, for at least one reader. Otherwise Trim Start is dropped (owner note) and the cue editor's click-to-seek is a known limit. |
| S4-b | For at least one combination, reported position minus a fixed offset is within 20 ms at p95 and 40 ms at most. Offset recorded. Trim End stops within 20 ms. |
| S4-c | Cue lateness within 50 ms at p95 with pre-render where the product will run it (AUD-018). If only the render thread passes, ARCH 4.1's render thread is required. If only `timeBeginPeriod(1)` passes, the product sets it while presenting. |
| S4-d | A device change never crashes the program. Behaviour recorded per output. |
| S4-e | Playing adds no more than about 20 MB working set (streamed). Open times recorded. |
| S5-a | No skipped or doubled second in 12 minutes. Every value shows within 100 ms of its whole second. |
| S5-b | Slot redraw under 2 ms per tick, CPU low. Fades with the timer drop no more frames than S2. |
| S5-c | Eyes: no flicker, no text shift, the color changes at the threshold. |

## Checklist items (eyes and ears)

S4-1 audio plays cleanly with the chosen combination (no crackle while slides change). S4-2 Sync: the flash and the click are together. S4-3 Tap: playback changes slide where you tapped. S4-4 device change: what happened, and whether resume worked. S4-5 click-to-seek feels immediate. S5-1 no flicker on monitor and projector. S5-2 digits don't move the text beside them. S5-3 warning color and minus sign. S5-4 timer readable during crossfades.
