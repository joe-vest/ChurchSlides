Size M, throwaway. Project: `spike/ChurchSlides.Spike` (new, WPF). No changes to `src/` or `tests/`.
FRD: PLT-001, PLT-002, PLT-003, PLT-005, PLT-006, PLT-008 (a) and (b), LIVE-010..012 (overlays, look only), LIVE-030/031, SLD-006 (fit modes), SLD-007 (decode at output size).
ARCH: 4.1 (threads), 7.1-7.3 (layers, pre-render, image pipeline), 7.5 (output display), 12 (S1, S2, S6, S7, S8).

**Status: agreed by the owner 2026-11-23 (all seven decisions). Ready to execute.**

## Goal

One program that the owner runs on the church PC, mostly over remote access, and that writes a results file. It answers: can a borderless Output sit exactly on the second monitor; is a 300 ms crossfade between real church backgrounds smooth on a Pentium E5400 with a GeForce 8400 GS; how long a slide takes to pre-render, and whether that must move off the UI thread; how much memory a typical Service takes; how long startup takes from a hard disk; and whether .NET 10 and WPF's hardware rendering work on this Windows 10 build. C0.3 (rich text) and C0.4 (audio, timer) add tabs to the same program.

## Target machine (from the owner, 2026-11-23)

Windows 10 Home 22H2 (19045.6466, no longer updated). Pentium E5400, 2 cores, x86-64-v1 only. 6 GB DDR2. GeForce 8400 GS, WDDM 1.2, driver from 2015. Hard disk. Two 1440×900 monitors at 100%: primary DISPLAY2 at (0,0), Output DISPLAY1 at (-1440,0), with a VGA splitter to the projector. The church's backgrounds are PNG and JPG in many shapes (16:10, 16:9, 4:3).

## C0.2a: Shell

- `spike/ChurchSlides.Spike/ChurchSlides.Spike.csproj`: `WinExe`, `net10.0-windows`, `UseWPF`, `FrameworkReference Microsoft.AspNetCore.App`, `app.manifest` with per-monitor DPI v2. No packages.
- `spike/publish.ps1`: publishes `out/r2r` and `out/plain`, prints folder sizes, zips both.
- `spike/README.md`: how to copy, unblock and run, which tabs need eyes, what to send back.
- `MainWindow`: tabs plus a status bar with working set, private bytes, managed heap, process CPU % and frame rate.
- `Metrics.cs` (sampling), `Results.cs` (figures plus checklist, writes the markdown file), `Monitors.cs` (`EnumDisplayMonitors`, `GetMonitorInfo`, `GetDpiForMonitor`).
- **System tab (S8):** Windows version and build (`RtlGetVersion`), .NET version, CPU name and instruction sets (`Sse41`, `Sse42`, `Popcnt`, `Avx2` `IsSupported`), WPF `RenderCapability.Tier`, every monitor's device name, pixel bounds and DPI.
- **Output tab (S1):** choose a monitor, open a borderless topmost window at its exact pixel bounds, showing a test pattern: 1-pixel lines on all four edges, corner marks, the bounds as text. The actual window rectangle (`GetWindowRect`) is compared to the monitor rectangle automatically. Checklist: all four edges visible on the second monitor, no taskbar, no flicker when it opens.
- **Startup (S7):** process start to first `ContentRendered`, JIT method count and time (`JitInfo`), with and without `--kestrel`. The README asks for one cold run after a reboot and one warm run.

## C0.2b: Slides

- `SlideFactory.cs`: decodes a background straight to output size (`DecodePixelWidth`/`Height`, `OnLoad`, frozen), applying Fit, Fill or Stretch. Text is drawn with `FormattedText` into a `DrawingVisual` with grayscale antialiasing. Each slide is two frozen 1440×900 bitmaps (background and text), as ARCH 7.2 says.
- `RenderThread.cs`: one STA thread with its own `Dispatcher` that runs the same factory and hands back frozen bitmaps.
- `SlideOutput`: the Output window's layers: two slide groups (background plus text), a Black, Clear and Logo overlay (`logo.jpeg`), Cut or Crossfade (100-1000 ms, default 300) by opacity animation. Keys: Right/Left (as the real hotkeys), B, C, L.
- `FrameMonitor.cs`: frame intervals during each transition, dropped frames, input-to-next-frame time for Cut (PLT-006).
- **Slides tab (S2):** pick backgrounds and a fit mode, open the Output, step through. Automatic run: 60 transitions each for Cut, Crossfade with pre-render on the UI thread, and Crossfade with pre-render on the render thread.
- **Memory tab (S6):** builds a typical Service (3 Songs of 6 slides, 5 Presentations of 5 slides, a Scripture item of 4 slides, with the church backgrounds), keeps 160×100 thumbnails of every slide and a 3-slide pre-render window, then auto-advances through it all. Records working set idle, loaded, presenting and after a full GC. Times each background: decode from the original (first and second read) and from a 1440×900 JPEG cache copy (ARCH 7.3).

## Pass criteria (proposed; final judgement at G0)

| # | Pass |
|---|---|
| S1 | Window rectangle equals the monitor's pixel rectangle. All four edge lines visible, no taskbar, no flicker. |
| S2 | Crossfade at 300 ms: on average under 1 dropped frame per fade with pre-render where it will run, CPU stays reasonable, and it looks smooth on the monitor. Otherwise Cut only (LIVE-031). |
| S6 | Working set ≤ 300 MB while presenting the typical Service (PLT-005). Cut: input to next frame < 100 ms (PLT-006). Pre-render time recorded. If pre-render stalls the UI thread over about 10 ms, the product uses the render thread (ARCH 4.1). |
| S7 | Numbers recorded. The owner judges them acceptable (as a guide: warm ≤ 3 s, cold ≤ 10 s). |
| S8 | Runs. `RenderCapability.Tier` is 2 (hardware). Instruction sets recorded. Whether to accept Windows 10 without updates is the owner's call at G0. |
